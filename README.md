# cheetah-agent

Агент на LangGraph, отвечающий на произвольный вопрос, требующий:
1. поиска фактов во внешней среде (Wikipedia),
2. рассуждения над ними (CoT),
3. самопроверки результата (независимый пересчёт "с нуля").

Пример из тестового задания — «сколько времени потребуется гепарду, чтобы пересечь Москву-реку по Большому Каменному мосту» — нигде не зашит в код: в промптах нет ни слова про гепардов и мосты, только общая инструкция «найди факты, посчитай, перепроверь». Вся предметная логика живёт исключительно в данных, которые агент сам находит в Wikipedia. Полная исходная спецификация — в [architecture.md](architecture.md); этот README объясняет, почему она реализована именно так, и что делать, если что-то пойдёт не так при проверке.

## Почему такая архитектура

| Решение | Почему |
|---|---|
| Жёсткий линейный пайплайн, а не ReAct-цикл | Предсказуемее и проще проверять шаг за шагом, чем свободный цикл «думай-действуй»; явный CoT в `reason_node` всё равно даёт видимое рассуждение, просто без риска, что модель зациклится на выборе следующего действия. |
| LangGraph | Узлы — обычные чистые функции `(state) -> dict`, граф явно описывает workflow и его единственную точку ветвления (retry). Никакой скрытой оркестрации. |
| Одна retry-петля `validate → search` | Общий, предметно-независимый механизм отказоустойчивости: Wikipedia не обязана отдать нужный факт с первой попытки поисковых запросов. Ограничена `MAX_RETRIES`, чтобы не уйти в бесконечный цикл. |
| Без отдельного calculator-tool | Простая арифметика (перевести км/ч в м/с, разделить расстояние на скорость) не требует отдельного вызова инструмента — современные модели считают её надёжно прямо в тексте рассуждения. Лишний tool call добавил бы задержку без функциональной пользы. |
| Самопроверка в отдельном независимом вызове LLM | Модель, которую просят «проверь сам себя» в том же контексте, где она уже дала ответ, склонна соглашаться сама с собой. Отдельный вызов с другим промптом («пересчитай с нуля, не доверяя рассуждению») ловит ошибки заметно надёжнее. |
| Многоязычный поиск (ru/en) | Разные факты вероятнее находятся в разных языковых версиях Wikipedia (например, характеристики моста — в ru, максимальная скорость животного часто подробнее расписана в en). |

## Как это работает по шагам

```
question
   │
   ▼
┌─────────┐   search queries (ru/en)
│ search  │──────────────────────────────┐
└─────────┘                               │
   ▲                                      ▼
   │                                 ┌─────────┐
   │                                 │  wiki   │  Wikipedia: search + fetch
   │                                 └─────────┘
   │                                      │ raw article texts
   │                                      ▼
   │                                 ┌─────────┐
   │                                 │ extract │  LLM → факты в JSON
   │                                 └─────────┘
   │                                      │ facts[]
   │                                      ▼
   │                                 ┌─────────┐
   │                                 │ reason  │  LLM → CoT + answer
   │                                 └─────────┘
   │                                      │
   │                                      ▼
   │                                 ┌──────────┐
   │                                 │ validate │  независимый пересчёт "с нуля"
   │                                 └──────────┘
   │                                      │
   │              INVALID (retry_count < MAX)     VALID  или  retry_count >= MAX
   └──────────────────────────────────────┘              │
                                                           ▼
                                                          END
```

Всё реализовано в `agent/graph.py`. По каждому узлу — что он делает и на каких неочевидных решениях в промптах это держится:

- **`search_node`** — превращает вопрос в 2–5 поисковых запросов с указанием языка. Промпт требует, чтобы запрос был точным названием статьи, а не описательной фразой вроде «длина моста»: лишние слова сбивают полнотекстовый поиск MediaWiki на нерелевантные статьи. При retry в промпт добавляется причина отказа от `validate_node`, чтобы модель скорректировала запросы, а не повторила их один в один.

- **`wiki_node`** — по каждому запросу ищет кандидатов (`search_wikipedia`) и забирает полный текст топ-2 статей (`fetch_article_text`), обрезая каждую до `max_chars` символов (см. `agent/tools.py`).

- **`extract_node`** — превращает сырые тексты статей в структурированные факты `{entity, property, value, unit, source_text, confidence}`. Промпт требует точно размечать `entity` по эпохе/версии объекта — например, `"Большой Каменный мост (современный, с 1938)"` отдельно от `"Всехсвятский каменный мост (исторический предшественник, XVII век)"`. Это нужно, потому что статьи Wikipedia часто в одном тексте описывают и текущее состояние объекта, и его более раннюю версию/предшественника — без явной разметки по эпохе агент рискует подставить историческое значение вместо текущего.

- **`reason_node`** — пошаговый CoT на основе фактов, вычисления прямо в тексте рассуждения, финальный `answer`.

- **`validate_node`** — независимый вызов с другим промптом: пересчитать с нуля, не доверяя рассуждению, и явно проверить (среди прочего) — не относится ли использованный факт к прошлому состоянию сущности вместо текущего. В JSON-схеме поле `reason` стоит раньше `status`: порядок полей в structured output задаёт порядок генерации токенов, поэтому модель сначала честно рассуждает, и только потом присваивает вердикт по итогам этого рассуждения, а не наоборот.

Все LLM-вызовы используют OpenAI-совместимый structured outputs (JSON Schema, `strict: true`) — модель физически не может вернуть невалидный по схеме JSON, парсинг ответа не требует хрупких regex/try-except.

## Инструменты и почему они

- **LangGraph** — граф с чистыми функциями-узлами и одним явным условным переходом (retry), см. выше.
- **OpenAI-совместимый клиент** (`agent/llm.py`) с настраиваемыми `BASE_URL`/`MODEL_NAME` — провайдер-агностично: под капотом можно использовать любой OpenAI-совместимый эндпоинт (в разработке использовался `cloud.ru`, модель `deepseek-ai/DeepSeek-V4-Pro`; должен работать и с обычным OpenAI API).
- **`requests` напрямую к MediaWiki API** (`agent/tools.py`), а не пакет `wikipedia-api` из architecture.md — этот пакет не умеет полнотекстовый поиск, только получение конкретной страницы по названию. Два простых HTTP-вызова (`action=query&list=search` и `action=query&prop=extracts`) дают и поиск, и извлечение текста без лишних зависимостей.
- **`uv`** — управление окружением и зависимостями.
- **`a2a-sdk`** — для опциональной части (протокол A2A, architecture.md §5). Важно: реальный API пакета версии 1.1.2 заметно отличается от упрощённого наброска `execute(task) -> Task` в architecture.md — детали и грабли ниже, в отдельном разделе.

## Как проверить решение

Есть два независимых способа прогнать агента — оба вызывают один и тот же скомпилированный граф (`agent/graph.py:app`), просто с разной обвязкой сверху.

### 1. Напрямую, без сервера

```bash
uv run main.py "Сколько времени потребуется гепарду, чтобы пересечь Москву-реку по Большому Каменному мосту?"
# --debug добавляет подробный лог по узлам графа, HTTP- и LLM-вызовам
```

Вывод содержит цепочку рассуждений (CoT), итоговый ответ и статус валидации с числом использованных retry.

### 2. Через A2A-сервер (опциональная часть, architecture.md §5)

Граф также доступен по протоколу [A2A](https://a2a-protocol.org/) через тонкий адаптер `agent/a2a_agent.py:CheetahBridgeAgent` — вся логика остаётся в `app`, обёртка только извлекает вопрос из входящего сообщения и кладёт ответ обратно в очередь событий.

Нужно два терминала (сервер работает, пока открыт, — сам не завершается):

**Терминал 1 — поднять сервер:**

```bash
uv run python a2a_server.py
# JSON-RPC сервер на http://127.0.0.1:9999
# agent card: http://127.0.0.1:9999/.well-known/agent-card.json
```

**Терминал 2 — отправить вопрос через A2A-клиент:**

```bash
uv run python a2a_client.py "Сколько времени потребуется гепарду, чтобы пересечь Москву-реку по Большому Каменному мосту?"
# --url для другого адреса сервера, --timeout для другого HTTP-таймаута (по умолчанию 300с —
# полный прогон графа с ретраями по вызовам LLM может занимать несколько минут)
```

Формат вывода `a2a_client.py` совпадает с `main.py` (CoT / Answer / validation) — под капотом ответ приходит как A2A `Message`, где текст ответа лежит в `parts[0].text`, а CoT/статус валидации/число retry — в `metadata`.

Остановить сервер — `Ctrl+C` в терминале 1 (или `pkill -f "python a2a_server.py"`).

### A2A: важные детали реализации

Пакет `a2a-sdk` 1.1.2 использует protobuf как основной формат (`a2a.types.Message`/`Part`/`Role` — реэкспорт классов `a2a_pb2`), а не упрощённый пример из architecture.md. Ключевое: `AgentExecutor.execute(context, event_queue)` кладёт в очередь **один `Message`** («immediate response» workflow) — полноценный `Task`/`TaskUpdater` с промежуточными статусами не нужен, потому что наш агент не стриминговый, а классический запрос-ответ.

Если вы тестируете сервер вручную через `curl` (а не через `a2a_client.py`), учтите: SDK требует HTTP-заголовок **`A2A-Version: 1.0`**. Без него он по умолчанию считает, что клиент говорит на версии протокола `0.3`, и отклоняет запрос с ошибкой `VERSION_NOT_SUPPORTED` — на эту ошибку легко напороться при ручном тестировании curl'ом, если забыть заголовок.

## Практические заметки

- Wikipedia может вернуть `429 Too Many Requests` при частых повторных запросах подряд — не баг агента, просто нужно немного подождать и повторить. Описательный `WIKI_USER_AGENT` в `.env` (см. `.env.example`) снижает риск троттлинга согласно [политике Wikimedia](https://meta.wikimedia.org/wiki/User-Agent_policy).
- `LLM_TIMEOUT_SECONDS` в `.env` стоит подстроить под свою модель/эндпоинт, если LLM отвечает медленно.

## Известные ограничения

Честно о слабых местах, а не только о том, что работает:

- `max_chars` в `fetch_article_text` — фиксированный потолок (по умолчанию 12000 символов на статью). Очень длинные статьи всё ещё могут обрезаться до нужного факта — в разработке уже ловили случай, когда нужное число оказывалось на 6150-м символе при лимите 6000.
- Точность разметки факта по эпохе (текущий/исторический) в `entity` зависит от промпта и качества модели — это существенно снижает, но не исключает полностью риск подмены исторического значения текущим.
- `MAX_RETRIES` ограничивает число попыток самокоррекции; после исчерпания граф возвращает лучший найденный ответ с явной пометкой `INVALID`, если самопроверка так и не прошла, — не «правильный ответ любой ценой».
- Точность поиска в Wikipedia зависит от способности модели угадать точное (или близкое) название статьи — для менее известных сущностей поиск может не найти нужную статью с первой попытки.

## Структура репозитория

```
.
├── agent/
│   ├── config.py     # переменные окружения
│   ├── tools.py      # доступ к Wikipedia (search + fetch через MediaWiki API)
│   ├── llm.py        # вызов LLM со structured outputs
│   ├── graph.py       # состояние, узлы, сборка графа LangGraph
│   └── a2a_agent.py    # CheetahBridgeAgent — A2A-обёртка поверх графа
├── main.py            # CLI: прямой прогон графа
├── a2a_server.py       # поднимает CheetahBridgeAgent как A2A JSON-RPC сервер
├── a2a_client.py        # CLI-клиент: отправляет вопрос на a2a_server.py и печатает ответ
└── architecture.md    # исходная спецификация
```
